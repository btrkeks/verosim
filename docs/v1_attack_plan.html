1v1 Scope: Goals and Non-Goals

Scope decisions made 2026-06-12 (recorded as D8–D10 in the decision record):

In scope (v1)Out of scope (v1)

  • Tier A + Tier B symbol categories (Section 3); Tier C as stretch
  • Validation against the Python musicdiff oracle, tier-matched via DetailLevel
  • Fast batch CLI, parallel over score pairs (one Toolkit per thread, per D7)
  • Performance benchmark vs. Python on real corpus data
  • Cross-importer normalization (D8): small metric differences between MusicXML- and kern-sourced trees of the same piece are accepted; we measure the gap but do not engineer it away

  • DetailLevel-style user-facing configurability (internal tier switch only)

The single sentence that defines success: by the end of week 4 we can run verosim pred.krn gt.xml (or any format combination) over thousands of pairs, orders of magnitude faster than Python musicdiff, with tier-matched scores that correlate ≥ 0.95 with the Python oracle on the validation corpus.

Pipeline-stage layout: each dataset is a staged pipeline, not a flat pool. Stage 0_raw_xml / 0_raw_ekern holds the originals (pdmx’s raw XML is archived compressed as 0_raw_xml.tar.zst); 1_kern_conversions is the kern conversion of those originals; stages 2_, 3_, 4_, … are progressively filtered/cleaned/normalized derivatives of the same samples. 3Taxonomy Tiers

The OMR-NED categories, ordered by frequency in real scores and implementation dependency. Each tier is independently shippable and independently testable against the oracle (Section 4).

TierCategoriesPlan status
Tier A Note pitch, accidental, note head, dots, flags/beams (as duration symbols), rests; clef, key signature (per accidental), time signature (per component). Measure alignment, voice/chord handling, offset computation. v1 core — M2/M3
Tier B Ties, slurs, articulations, dynamics (incl. hairpin duration symbol), grace notes (+slash). v1 core — M4
Tier C Ornaments, text directions (per character). v1 stretch — M5 if on schedule
Tier D Lyrics (per character + verse number; explicitly excluded from v1, user decision 2026-06-12), ottavas, arpeggios, chord symbols, endings, tremolos, style details (stem direction, color). Post-v1

Note on lyrics: the lieder corpus is full of them, so every v1 oracle comparison must exclude lyric symbols on both sides — this is exactly what tier-matched DetailLevel oracle runs give us. Excluding lyrics from v1 also keeps the per-character symbol machinery out of the core entirely (text directions, the other per-character category, are stretch-only).

4Core Strategy: Tiered Oracle Validation

The single most important methodological idea in this plan: at every stage, compare like with like. Python musicdiff exposes DetailLevel flags (musicdiff/musicdiff/detaillevel.py) that restrict which notation features participate in the comparison. We exploit this so that the oracle is always scoped to the tiers the C++ side has implemented:

Tier A complete  →  oracle run with DetailLevel ≈ NotesAndRests + Signatures
Tier A+B         →  oracle run adding Ties, Slurs, Articulations, Dynamics
Tier A+B+C       →  oracle run adding Ornaments, Directions (lyrics always excluded in v1)

This converts “does the whole thing agree at the end?” (one giant, late, undebuggable comparison) into a sequence of small, early, debuggable comparisons. When a tier-matched run disagrees on a pair, the disagreement is localized to the tier just added.

Two practical consequences:

  • The oracle is precomputed and cached. Python musicdiff is slow — that is the whole premise. The harness runs it once per (pair, DetailLevel) combination, in parallel, and stores results as JSON keyed by content hash. Oracle computation for DEV-200 starts on day 1 (M1) and runs in the background; it is never on the critical path.
  • The exact DetailLevel-to-tier mapping is itself a deliverable of M1 — it must be pinned down by reading detaillevel.py precisely, not assumed.

M1Oracle harness & corpora Days 2–4 (overlaps M0)

Work:

  • Define and commit the DEV-200 / HOLDOUT-100 / PERF-10K file lists (fixed-seed sampling scripts, lists checked in).
  • Python harness (harness/): runs musicdiff on a pair at a given DetailLevel, emits JSON {pair, detail, distance, n1, n2, omr_ned, runtime, error, edit_ops}; tolerates and records music21 parse failures (coverage is a measured number, not an assumption). Parallel driver + content-hash cache. edit_ops is musicdiff’s per-edit operation list — stored so that rung-4 divergence triage is “diff two operation lists”, not “stare at two scalars”; this is the cheapest schedule insurance for the M3 contingency budget.
  • Pin the DetailLevel↔tier mapping by reading detaillevel.py; record it in the decision doc.
  • Kick off background oracle precomputation: DEV-200 at the Tier-A-equivalent DetailLevel first, then Tier A+B.
  • Mutation corpus generator: a script that applies single, controlled textual mutations to small kern files (change one pitch letter, delete one accidental, drop a dot, remove a barline’s note …) and records the analytically expected cost per the paper’s rules. ~50 mutation cases, including key-signature/accidental-state cases (same written note with and without a governing key signature, accidental carry within a measure) to pin the effective-pitch semantics that M2 must reproduce (D13). These are the unit-level ground truth that needs no oracle.
  • Mutation–oracle cross-check: run Python musicdiff over every mutation case and require analytic expectation = oracle output before any C++ tier implementation begins. The mutation costs encode our reading of the paper; a mismatch here means we misread a costing rule — caught at the cheapest possible moment, before the misreading is enforced as a wrong spec by our own exact tests. Where paper and vendored code disagree, the vendored code wins (D12) and the disagreement is noted in the mapping doc.
  • Parse-coverage sweep: run verosim --dump-tree over PERF-10K, count load failures/warnings per dataset. This is cheap and tells us early whether Verovio’s humlib chokes on this kern dialect. Prerequisite (M0 review, D13): VrvBridge currently pins Verovio logging to LOG_ERROR, which suppresses the warnings this sweep is supposed to count — make the log level a constructor parameter (or capture warnings via Verovio’s string-capture logging) first; the same hook is what deferred D4 will eventually consume.

Exit criteria: oracle JSON (incl. edit_ops) exists for ≥ 150 of DEV-200 at Tier-A DetailLevel (music21 failures documented); mutation corpus with expected costs committed and cross-checked against the oracle with all mismatches resolved; Verovio parse coverage on PERF-10K reported (target > 95%; if far below, see risk R1).

M2Layer 2: Tier A symbol extraction Days 5–9

Work:

  • Define the v1 internal representation: SymScore → SymPart → SymMeasure → SymVoice → SymNote/SymRest, each carrying its OMR-NED symbol list. Mirrors musicdiff’s AnnScore shape (annotation.py) so the Layer-3 port maps 1:1.
  • Walk the Verovio tree (Score → Section → Measure → Staff → Layer): notes, rests, chords, beams, tuplets; read pitch/duration via PitchInterface/DurationInterface; clef/key/time from ScoreDef and inline changes.
  • Offset computation (the known-hard part, tackled first within M2): accumulate rational beat positions per layer; handle tuplet ratios and chords; grace notes get the paper’s treatment. Use exact rational arithmetic, no floats.
  • Effective pitch resolution (M0 review finding, D13): neither importer puts sounding pitch in the parse-only tree — iomusxml discards <alter> for regular notes (iomusxml.cpp:3140-3150), iohumdrum sets @accid only when the accidental is visible and no @accid.ges on the normal kern path (iohumdrum.cpp:26723+). Since musicdiff matches notes by sounding pitch, Layer 2 must resolve it: key signature + within-measure accidental carry + ties. Corollary: iohumdrum attaches an empty accid child to every pitched note — count accidental symbols by @accid value, never by element presence.
  • Document the MEI→symbol mapping table as it is written (companion table in the decision doc or a docs/mei_symbol_mapping.html).
  • Validate with symbol-count audits: verosim --count-symbols on HAND-10 must match the hand counts exactly; on DEV-200, total Tier-A symbol counts are compared against the oracle’s N values (not expected identical — parser differences, per D6 — but large or systematic gaps get investigated).

Exit criteria: HAND-10 symbol counts exact; DEV-200 Tier-A symbol counts within ~2% of oracle N values in aggregate, outliers triaged and explained.

Rungs 1–3 are exact and cheap — they run in CI on every change. Rung 4 is approximate and explicitly diagnostic: its job is to rank the most divergent pairs so debugging effort always goes to the worst offender first. The 0.95 threshold is provisional; if the measured ceiling (after triaging explained parser differences) is naturally lower, we document the revised threshold and the explanation rather than chasing an arbitrary number.

9Working Practices

How we work, day to day (adopted 2026-06-12, recorded as D11). Deliberately stated as concrete, checkable mechanics rather than named methodologies:

  • Fixtures before code. For every tier, the test fixtures — mutation cases with analytically expected costs and hand-counted symbol inventories — are written and committed before implementation of that tier begins. Verified at each milestone exit. The expected costs come from the paper, written down first, so the implementation can never quietly become its own specification.
  • Refactoring precondition: rungs 1–3 green. Refactor freely whenever the exact test rungs (symbol audits, mutation tests, identity tests) pass; never refactor while they are red. The exact rungs are the safety net; oracle correlation (rung 4) is diagnostic and is never a gate for refactoring.
  • Consolidation points at tier boundaries. Before starting Tier B (after the M3 gate) and before M5 hardening: up to half a day of cleanup-only work — no new features — with rungs 1–3 as the safety net.
  • Triage patches are marked and revisited. Fixes made under divergence-triage pressure (M3/M4) get a // TODO(consolidate) marker and are explicitly revisited at the next consolidation point, so gate-rescue hacks don’t calcify.
  • Milestone-exit plan review. At every milestone exit, ten minutes on one question: do the remaining milestones, estimates, and risk responses still hold? Exit-criteria results are appended to this document; any plan amendment is recorded as a new Dn in the decision record.
